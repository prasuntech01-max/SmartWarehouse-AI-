## 2. Metric Availability & Provenance Matrix

Every figure displayed in the UI, generated reports, or exports will carry a strict provenance classification:
- **`MEASURED`**: Directly measured wall-clock execution time (`perf_counter`), memory consumption (`tracemalloc`), or database-persisted event counts.
- **`SIMULATED`**: Discrete-time state variables produced directly by the simulation engine (`step_count`, `battery`, `total_distance`, `robot.pos`, `completed_tasks`).
- **`ESTIMATED`**: Derived or extrapolated values (e.g., A* shortest-path theoretical minimum, EWMA demand projection, shelf relocation distance savings, Gini coefficient).
- **`SIMULATED-TELEMETRY`**: Simulated IoT device sensor readings (temperature, smoke, gas, battery, motor temperature) generated by `core.sensor.Sensor` / `core.iot_manager.IoTManager`.

| Metric Name | Real Data Source | Provenance Label | Availability Status | Notes / Clarifications |
| :--- | :--- | :--- | :--- | :--- |
| **Warehouse Orders / Tasks** | `core.task_manager.WarehouseTask` | `SIMULATED` | **Available** | No separate "Order" class exists; `WarehouseTask` represents warehouse customer pick-and-pack orders. |
| **Completed Tasks & Throughput** | `sim.metrics.completed_tasks_count`, `sim.step_count` | `SIMULATED` | **Available** | Real counts tracked during simulation steps; throughput expressed as tasks/100 steps. |
| **Actual Collisions** | `sim.step()` position overlap check | `SIMULATED` | **Available** | Truly verified: if two robots occupy identical `(x, y)` at step $t$, collision is logged. Because Space-Time reservation works, actual count is 0. |
| **Conflicts Detected & Avoided** | `sim.metrics.detected_conflicts_count`, `MultiAgentPlanner.detect_conflicts` | `SIMULATED` | **Available** | Distinguishes between spatial conflicts prevented by reservation planning vs actual physical collisions. |

## 4. Database Schema Extensions (Forward-Only Migration 002)

Following repository conventions, SQLite database persistence will be safely extended using forward-only migration `persistence/migrations/002_module13_benchmarks_and_reports.sql`:

```sql
-- Migration 002: Module 13 Benchmarking & Report Metadata Storage

-- Stores benchmark execution runs
CREATE TABLE IF NOT EXISTS benchmark_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id TEXT UNIQUE NOT NULL,
    benchmark_name TEXT NOT NULL,
    parameters_json TEXT NOT NULL,
    environment_json TEXT NOT NULL,
    total_trials INTEGER NOT NULL,
    executed_by TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Stores individual trial observations
CREATE TABLE IF NOT EXISTS benchmark_trials (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id TEXT NOT NULL,
    algorithm_name TEXT NOT NULL,
    scenario_seed INTEGER NOT NULL,
    num_robots INTEGER NOT NULL,
    grid_size TEXT NOT NULL,
    obstacle_density REAL NOT NULL,
    execution_time_ms REAL NOT NULL,
    memory_peak_kb REAL NOT NULL,
    path_length INTEGER NOT NULL,
    optimal_path_length INTEGER NOT NULL,
    optimality_ratio REAL NOT NULL,
    conflicts_detected INTEGER NOT NULL,
    replan_count INTEGER NOT NULL,
    success INTEGER NOT NULL,
    FOREIGN KEY(run_id) REFERENCES benchmark_runs(run_id) ON DELETE CASCADE
);

-- Stores exported report snapshots and audit metadata
CREATE TABLE IF NOT EXISTS report_records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    report_id TEXT UNIQUE NOT NULL,
    title TEXT NOT NULL,
    generated_by TEXT NOT NULL,
    time_range_start TIMESTAMP,
    time_range_end TIMESTAMP,
    summary_json TEXT NOT NULL,
    export_format TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Indexing for fast historical querying
CREATE INDEX IF NOT EXISTS idx_bench_run ON benchmark_trials(run_id);
CREATE INDEX IF NOT EXISTS idx_report_time ON report_records(created_at);
```

## 5. Benchmarking Methodology & Scientific Rigor

1. **Strict Isolation**: Benchmarks run exclusively on **deep copies** of the warehouse grid and mock robot states. The active simulation loop, real-time reservation tables, and safety state are never touched.
2. **Deterministic Scenarios**: Standardized random seeds (`[101, 102, 103]`) produce reproducible obstacle layouts and task positions.
3. **Warm-up & Timing Precision**: Initial warm-up run is executed and discarded to eliminate JIT compilation or cache-miss bias; timing is measured using `time.perf_counter()` with sub-millisecond precision.
4. **Memory Profiling**: Python heap allocations are monitored via `tracemalloc` and labeled strictly as *Python Heap Peak*, not OS-level RSS.
5. **Statistical Metrics**: Every benchmark outputs `mean`, `median`, `standard deviation`, `min`, `max`, and `success rate` across repeated trials.
6. **Comparison Dimensions**:
   - Static 2D A* vs Space-Time 3D A* vs Multi-Agent Prioritized Planning.
   - Dispatch algorithms: Nearest Robot, Shortest Route, Priority-First, Workload-Balanced, Weighted Multi-Criteria, and Hungarian Batch Optimizer.
   - Scaling: Varying fleet size ($N \in [1, 2, 3, 4, 5]$) and obstacle densities ($0\%, 10\%, 20\%$).
7. **Transparent Limitations**: The UI and reports will state clearly:
   > *"Benchmark results reflect synthetic grid scenarios executed in Python 3.13 on the host CPU. Timings are subject to OS scheduling jitter and hardware variations."*

## 6. Explainable Recommendation Engine (Rule Catalogue)

All recommendations are strictly **advisory**, deterministic, and rule-based. They will never alter robot routes, reservations, or emergency states autonomously.

1. **`REC-ROBOT-UNDERUTILIZED`**:
   - *Condition*: Robot utilization $< 40\%$ while fleet average $> 70\%$ over the last 50 simulation steps.
   - *Evidence*: Specific robot busy ticks vs fleet average busy ticks.
   - *Advisory Action*: Suggest switching task dispatch strategy to `WORKLOAD_BALANCED` or `BATCH_OPTIMAL`.
2. **`REC-CONGESTION-BOTTLENECK`**:
   - *Condition*: Congestion index $\ge 60/100$ or $\ge 2$ intersecting paths in an aisle corridor.
   - *Evidence*: Coordinates of congested corridor cells and list of affected robot IDs.
   - *Advisory Action*: Suggest injecting a temporary detour waypoint or reassigning lower-priority robot tasks.
3. **`REC-BATTERY-DEPLETION-RISK`**:
   - *Condition*: Robot battery $< 25\%$ and Manhattan distance to nearest charging dock $> 8$ cells.
   - *Evidence*: Current battery percentage, current position, distance to dock.
   - *Advisory Action*: Flag robot for immediate return-to-dock upon current delivery completion.
4. **`REC-SHELF-LAYOUT-INEFFICIENCY`**:
   - *Condition*: High-frequency pick shelf ($> 30\%$ of total orders) located $> 10$ cells from packing stations.
   - *Evidence*: Shelf coordinate, order frequency, distance to station, and estimated travel savings.
   - *Advisory Action*: Propose swapping with low-demand perimeter shelf.
5. **`REC-PREVENTIVE-MAINTENANCE`**:
   - *Condition*: Robot health score $< 50/100$ based on cumulative distance ($> 150\text{m}$) and completed tasks ($> 10$).
   - *Evidence*: Cumulative travel distance, completed task count, battery wear score.
   - *Advisory Action*: Schedule diagnostic inspection at dock during next idle cycle.
6. **`REC-RECURRING-HAZARD-ZONE`**:
   - *Condition*: $\ge 2$ abnormal sensor readings or incidents in the same warehouse zone within 100 ticks.
   - *Evidence*: Zone bounds, incident types (e.g. Temperature / Gas), sensor IDs.
   - *Advisory Action*: Inspect environmental HVAC and restrict autonomous routing through affected zone.

## 7. 3D Digital Twin Enhancements & Trace Budget ($\le 40$ Traces)

1. **Layer-Based Architecture**: Modular trace builders (`build_static_scene`, `build_robot_traces`, `build_path_traces`, `build_sensor_markers`, `build_hazard_overlays`).
2. **Batching Strategy**:
   - All static storage racks are grouped into a single combined `go.Mesh3d` cuboid trace.
   - Perimeter safety walls and charging docks are vectorized.
   - Movement trails are consolidated into unified traces.
   - Total Plotly trace count is strictly maintained $\le 36$ traces (well below the 40-trace budget).
3. **Interactive Visual Enhancements**:
   - Robot status beacons (moving, picking, delivering, docked, emergency hold).
   - Sensor field-of-view discs (ultrasonic, infrared, thermal).
   - Pulsing hazard zones (yellow warning, red emergency perimeter).
   - Camera presets: `Isometric (45°)`, `Top-Down (2D-Orthographic)`, `Front Elevation`, `Side Aisle`.
4. **Resilience & Fallback**:
   - If WebGL / Plotly rendering fails, the system automatically falls back to the 2D Matplotlib warehouse floorplan with an informative banner.

## 8. Export & Reporting Architecture (Zero Required Dependencies)

1. **CSV Export**:
   - Clean tabular downloads for Fleet Telemetry, Task Lifecycle, Incident History, and Benchmark Trials.
   - Exported with `UTF-8-SIG` (UTF-8 with BOM) for instant compatibility with Microsoft Excel on Windows.
   - **CSV Injection Defense**: Cells starting with `=`, `+`, `-`, or `@` are safely prefixed with a single quote `'` to neutralize formula execution in spreadsheet software.
   - Passwords, secret keys, and raw tokens are strictly stripped.
2. **Self-Contained Executive HTML Report**:
   - Fully styled, standalone HTML document with embedded CSS.
   - Print-optimized (`@media print` rules, page breaks, clean typography).
   - Users can open the report in any browser and press `Ctrl+P` ("Save as PDF").
3. **Comprehensive Report ZIP**:
   - Combines the Executive HTML summary, all CSV data tables, and a cryptographic `MANIFEST.txt` (containing generation timestamp, SHA-256 checksums, and generating operator username).

## 9. Security, Role-Based Access & Audit Integrity

- **Role Permission Matrix**:
  - `ADMIN`: User management, database maintenance, benchmark runs, report generation/export, incident acknowledgment/override, system settings.
  - `OPERATOR`: Simulation controls, task creation & dispatch, benchmark runs, report generation/export, incident acknowledgment/clear.
  - `VIEWER`: Read-only access to live simulation, 3D digital twin, stored analytics, completed benchmark comparisons, and system telemetry. All mutating buttons and export controls are hidden and guarded server-side.
- **Audit Logging**: Every report export, benchmark execution, task cancellation, and emergency clearance is permanently recorded in the database audit log with user identity and timestamp.
